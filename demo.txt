# 2. Problem kya hai?

Traditional honeypot ka basic kaam hota hai:

```text
Attacker
   ↓
Honeypot
   ↓
Logs
```

Problem ye hai ki security team ko mostly **raw logs** milte hain.

Example:

```text
10:30:01 connection from 192.168.x.x
10:30:04 login failed
10:30:08 login successful
10:30:12 whoami
10:30:18 ls
10:30:25 /admin accessed
```

Ye logs useful hain, lekin security analyst ko manually samajhna padta hai:

* attacker kya kar raha tha?
* attack kitna dangerous hai?
* attacker ka behavior kya hai?
* koi IOC mila?
* kaunsa MITRE technique use hua?
* kya ye attack kisi previous attack jaisa hai?
* attacker ka possible objective kya hai?
* report kaise banegi?

**Yahi hamara main problem hai.**

# 12. Risk Score kaise niklega?

AI ko directly:

Example:

```text

Suspicious file activity      +20

```

Then:

```text
0–30   LOW
31–60  MEDIUM
61–80  HIGH
81–100 CRITICAL
```

Example:

```text
Risk Score = 74
Risk Level = HIGH
```

# 32. AI hallucination kaise rokoge?

Judge pooch sakta hai.

Answer:

> “We don't allow the LLM to freely analyze an uncontrolled environment. We first normalize and process the telemetry using deterministic engines. The AI receives structured evidence and is instructed not to invent IPs, commands, IOCs or MITRE mappings. If evidence is insufficient, it must explicitly say so.”

This is a **very good answer**.

---

# 33. Why AI required?

Judge:

> “Why did you use AI? Rules se ho sakta tha.”

Answer:

> “Rules are effective for deterministic tasks such as IOC extraction, risk scoring and evidence-based MITRE mapping. But raw security telemetry is difficult for humans to interpret quickly. We use AI for higher-level reasoning such as explaining the attack, generating an attack story, identifying a possible objective, correlating evidence and producing analyst-friendly threat reports.”

---

# 34. Why not use AI for everything?

Answer:

> “Because security decisions should remain explainable and evidence-based. We therefore keep detection, IOC extraction and risk scoring deterministic, while using AI mainly for interpretation, summarization and analyst assistance.”

🔥 Very strong answer.

---

# 35. Why honeypot?

Judge:

> “Why not just monitor a real server?”

Answer:

> “A honeypot provides a controlled environment specifically designed to attract and observe suspicious activity. It allows us to collect attacker behavior without exposing production systems, while giving us high-value telemetry for threat intelligence.”

---

# 36. Why multiple honeypots?

Answer:

> “Different services expose different attacker behaviors. SSH can reveal authentication and command activity, while Web and API honeypots reveal HTTP requests, endpoint discovery and application-level behavior. Combining them gives us richer attacker profiles.”

---

# 37. Why PostgreSQL?

Answer:

> “Our platform has relational entities such as sessions, events, IOCs, attackers, MITRE mappings and reports. PostgreSQL provides structured persistence and makes correlation and querying easier.”

---

# 38. Why WebSocket?

Answer:

> “Security monitoring is time-sensitive. WebSocket allows newly captured honeypot events to appear on the SOC dashboard in real time without repeatedly refreshing the page.”

---

# 39. Why Docker?

Answer:

> “Honeypots are intentionally exposed to suspicious activity, so isolation is important. Docker provides lightweight service isolation and makes deployment and replication easier.”

---

# 40. Why Parrot OS?

Simple answer:

> “We use Parrot OS as a controlled attacker simulation environment to generate realistic but authorized activity against our own honeypots.”

---

# 41. Is this a real attack?

Answer:

> “No. Our demo uses controlled and authorized activity against our own honeypot inside an isolated network. We don't target public systems, third-party infrastructure or real organizations.”
